# Team agent isolation (Stage 2)

Stage 1 ([../multi-agent-team/](../multi-agent-team/README.md)) gave every
team agent its own folder and persona, but its tools still run on the host.
Stage 2 gives each team agent **its own container** for shell and file work,
behind a supervisor that alone holds the Docker socket, with every tool off
until the owner turns it on. Modelled on OpenDots' container-per-Dot design.

## Decisions already made

| Decision | Why |
| --- | --- |
| Tools reach the container through the runtime's existing **custom (SDK) tools**, answered by the backend; no runtime patch | `configure_tools` already supports `enabled: []` plus callback tools (`probe_model` uses it). One runtime process stays; nothing in `runtime/` changes |
| A team agent session gets `enabled: []` — no built-in and no MCP tools at all — plus only the switched-on container tools | Allowlisting nothing is the only fail-closed choice: the runtime has dozens of host-touching tools, and MCP connectors run on the host with the owner's credentials |
| The guard also triggers on the session's folder being inside `AMIRO_AGENTS_ROOT`, not only on the chat route's `agentId` | Any future caller that forgets the toolset still cannot give a team agent host tools |
| The supervisor is a small Rust binary in this repo (`backend/sandboxd`), not OpenBot's | Same language and build as the backend, shares the credential and path code, no Node/Bun or GitHub-fetched build context, and a narrower API (no screen service in Phase 00) |
| The supervisor runs in a container with `cap_drop: ALL`, `no-new-privileges`, read-only rootfs, non-root + docker group, port on `127.0.0.1` only | Mirrors OpenDots' compose hardening; the socket is the most powerful thing on the box, so its holder must be the least privileged process that can use it |
| Agent containers run as the **owner's uid:gid**, never 0 | The bind-mounted folder is owned by the Amiro user; a fixed uid 1000 could not write it without chown. Non-root is what matters; uid 0 is refused |
| Files are read and written **inside the container** (exec / archive API), not by the backend on the host folder | An agent with `shell` can plant a symlink in its folder; host-side file access would follow it out. Inside the container it resolves to the container's own view |
| Per-agent credential = `HMAC-SHA256(master, "amiro-agent:" + id)`, required on every agent-scoped supervisor route alongside the supervisor token | OpenDots' derivation; a leaked credential for one agent cannot drive another's container, and the master never leaves backend + supervisor |
| The credential is not injected into the container in Phase 00 | Nothing inside the container calls back yet; adding it later is a Phase 02 decision |
| Secrets live in `$AMIRO_HOME/sandbox/supervisor.env` (0600), generated by `scripts/sandbox.sh` | Operator config, not a user secret: it never needs to pass through the UI or chat, and the backend and compose read the same file |
| Default network is bridge (internet on), `none` available globally in Phase 00; per-agent egress is Phase 01 | Matches OpenDots' documented default; honest about it in the UI-facing docs |
| Browser is a stored policy key but is **rejected** until Phase 03 and not shown in the UI | Honest-product rule: no switch for a capability that does not exist |
| The main agent is unchanged | It is the owner's own agent working in `~/.amiro/workspace`; the VM is its boundary (`docs/SECURITY-MODEL.md`) |
