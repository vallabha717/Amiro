title: "Credentials"
description: "Store API keys and secrets so the agent can use them without ever seeing their values."

The credential vault holds API keys and tokens for services your agent calls. Secrets are encrypted at rest, and every list shows only metadata and a masked hint.

<Warning>
The credentials page is at `/admin/credentials` and is owner-only. Reads require a signed-in user, but adding, editing, deleting, validating, and brokered calls are admin-only.
</Warning>

## Add a credential

<Steps>
  <Step title="Open the page">
    Go to Admin, then **Credentials**, or open `/admin/credentials`.
  </Step>
  <Step title="Start from a preset (optional)">
    Quick presets fill the common fields for GitHub, OpenAI, 9Router, Composio, Slack, or a custom entry.
  </Step>
  <Step title="Enter service, field, and secret">
    The service and field form a slot such as `github/token` or `openai/api_key`. Type the secret into the password field. The show toggle only reveals what you are typing, never a stored value.
  </Step>
  <Step title="Add optional details">
    Expand **Optional details** to set a label, agent guidance (a short usage description), and comma-separated allowed domains. A live preview shows the environment variable name this slot will export.
  </Step>
  <Step title="Save">
    The secret is encrypted and written to the vault. The list then shows the slot, its masked hint, and the exported variable.
  </Step>
</Steps>

## What the list shows

Each row shows the masked hint (for example `••••1234`), the generated `$AMIRO_CRED_<SERVICE>_<FIELD>` variable with a copy action, allowed domains if set, and any agent guidance. The plaintext value is never part of a response.

Use the search box to filter rows by service, field, label, usage description, hint, variable name, or allowed domains.

## How the agent uses a credential

The vault is designed so a secret can be used without ever entering the model's prompt or the transcript.

- **Environment reference.** Each slot exports an environment variable named `$AMIRO_CRED_<SERVICE>_<FIELD>` (upper case, non-alphanumerics become `_`) to the processes the runtime starts. In chat, the agent can reference that variable in a shell command, or in an MCP server header, instead of the literal value.
- **Brokered request.** For HTTP APIs, the agent can ask Amiro to make the request server side. Amiro injects the secret into a header, checks the host against the credential's allowed domains, and scrubs the secret from the response before returning it. An empty allowed-domains list means no host restriction, so set domains when you want the credential limited to specific hosts.

The prompt block the agent sees lists slots, labels, guidance, and allowed domains only. Its own instruction is to reference credentials by variable name or through a brokered call, never to print a raw value.

## Rotation and deletion

- **Rotate** by adding the credential again with the same service and field, then saving the new secret. The slot is overwritten.
- **Delete** from the row action. A confirmation warns that agents will lose access immediately.

<AccordionGroup>
  <Accordion title="Where the keys live">
    Secrets are encrypted with AES-256-GCM under the app's `protected/` directory, with a random nonce per write and a 32-byte master key. Each ciphertext is bound to its `service/field` slot, so a value copied to another slot fails to open.
  </Accordion>
  <Accordion title="Why lists never show values">
    Routes return slot metadata plus the backend-computed masked hint. Plaintext is produced only for server-side use, and errors that reflect an upstream body have the secret replaced with a redaction marker.
  </Accordion>
  <Accordion title="Environment variables versus brokered calls">
    A credential exported into the runtime environment is readable by local tools and processes the runtime starts, such as a shell command. A brokered call keeps the secret server side and scrubs it from the response. Use brokered calls when you can, and keep the machine itself trusted.
  </Accordion>
</AccordionGroup>

<Warning>
The vault's master key sits beside the encrypted file, protected by OS file permissions. That protects against casual disclosure such as a backup, a screenshot, or the UI. It is not process isolation, and it is not a keychain prompt. Secrets passed to the runtime as environment variables are visible to that process and its children.
</Warning>

<Note>
Provider sign-in keys are different from vault credentials. Connecting a chat provider through `/login` or the providers page stores that key in the runtime's own credential layout. Use the vault for arbitrary services your agent calls, and the provider flows for chat models.
</Note>
